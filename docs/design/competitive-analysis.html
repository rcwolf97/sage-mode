Competitive Analysis

A second no-context agent, this time with full access to all four repos — gstack and compound-engineering each win decisively on their own headline strength, plus a live sage-careful regression found and fixed

Method note: All claims below are grounded in the actual files on disk. Path:line citations point at real code, hook scripts, or SKILL.md/agent-brief prose (which I'm treating as executed artifact, not documentation about the artifact). Where I ran a hook directly against a crafted input to verify behavior, I say so and show the input/output. Where a claim rests only on a doc file's own words (including sage-mode's docs/research/scorecard.md), I flag it as self-reported and unverified. Line numbers reflect the files as read during this review (2026-08-25).

Part 1 — What each of the three does well

gstack: a real code-intelligence + persistent-memory layer, with a fail-closed provider abstraction

gstack's standout mechanism is gbrain integration: semantic (embedding-based) code search plus symbol/call-graph navigation, layered on top of cross-session and cross-machine persistent memory, wired through a genuinely engineered provider-abstraction contract rather than a single hardcoded integration.

  • USING_GBRAIN_WITH_GSTACK.md documents a full lifecycle: gbrain search "browser security canary" for semantic hits, gbrain code-def/code-refs/code-callers/code-callees for call-graph navigation (lines 22–24), a per-repo trust triad (read-write / read-only / deny) so a consultant's Client-A insights can't leak into a brain Client B can search (lines 93–104), and a documented embedding-model choice (voyage-code-3, chosen because it beat voyage-4-large and OpenAI text-embedding-3-large head-to-head on this codebase's symbol queries, line 62).
  • This isn't just a doc's promise — lib/code-intelligence/contract.ts defines a real, typed provider interface (CodeProvider, lines 110–127) with three concrete adapters (gbrain-adapter.ts, graphify-adapter.ts, sourcebot-adapter.ts), a closed failure-code set (CODE_PROVIDER_FAILURES, lines 129–138) so a typo can never mint an untyped failure, and — notably — a fail-closed egress-consent gate: assertEgressConsent() (lines 188–201) throws PROVIDER_NOT_CONSENTED unless the provider is local or the caller explicitly passed consented: true. Nothing in this repo silently ships repo content off-machine.
  • The whole thing degrades gracefully: resolveCodeProvider() returns null when no provider is available/consented, and callers fall back to grep (contract.ts, lines 8–11) — "never a dependency, always an enhancement."

This is the single feature none of the other three repos have any real analog to: durable, retrieval-ranked, semantically-searchable memory of what an agent has learned and where code lives, with an engineered consent/degradation model around it.

compound-engineering-plugin: verified cross-model adversarial review

compound-engineering-plugin's standout mechanism is cross-model review with a verified model-identity receipt, implemented in skills/ce-code-review/scripts/cross-model-adversarial-review.sh (duplicated byte-for-byte into ce-doc-review and ce-pov, and kept in parity by tests/cross-model-receipt-parity.test.ts).

  • The script dispatches the same diff to genuinely different model providers/routes — codex, claude, grok-cli, grok-cursor/cursor-agent, composer — each sandboxed to read-only, no-mutate permission modes (lines ~220–267).
  • Critically, it does not just trust that the requested model served the request. extract_model_receipt() (lines 169–209) reads the actual response envelope for routes that report one (Claude's modelUsage field on the terminal type=result NDJSON event) and compares the served model id's family prefix against what was requested via expected_model_prefix() (lines 116–124). Routes that cannot supply a receipt are explicitly labeled "unverified" (route_receipt_supported(), lines 99–103; MODEL_ACTUAL="unverified" default, line 170) rather than silently assumed correct.
  • tests/cross-model-receipt-parity.test.ts enforces that this receipt-extraction "kernel" stays byte-identical across all three review skills that use it (lines 1–41), so the guarantee doesn't quietly drift in one copy and not another.
  • This whole idea has a name in the project's own vocabulary (CONCEPTS.md, "Model identity receipt": "verified only by such a receipt — never by the request parameters or the model's own text").

This is the thing that makes compound-engineering-plugin's "independent second opinion" claims actually independent and actually verified, rather than assumed.

superpowers: rationalization-resistant, pressure-tested skill prose

superpowers' standout mechanism is not any single skill's content — it's a uniform, load-bearing anti-rationalization design pattern applied across the whole library, developed through an explicit RED/GREEN/REFACTOR methodology for testing prose against a model under pressure, not just for correctness.

  • Every discipline-enforcing skill follows the same shape: an "Iron Law" stated as an unconditional rule (systematic-debugging/SKILL.md line 16: NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST; verification-before-completion/SKILL.md line 17: NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE), a "Common Rationalizations" table of excuse → reality pairs harvested from what agents were actually observed saying (systematic-debugging/SKILL.md lines 244–255; verification-before-completion/SKILL.md lines 61–72), and a "Red Flags" list of self-catchable thought patterns (using-superpowers/SKILL.md lines 33–50: e.g. "I need more context first" → "Skill check comes BEFORE clarifying questions").
  • using-superpowers/SKILL.md (lines 10–16) makes invocation itself non-negotiable: "IF A SKILL APPLIES TO YOUR TASK, YOU DO NOT HAVE A CHOICE... This is not negotiable. You cannot rationalize your way out of this."
  • Crucially, this isn't asserted to work — it's built via a documented process. writing-skills/testing-skills-with-subagents.md (lines 1–46) describes TDD applied to prose: run a scenario with pressure and no skill, watch a real subagent fail and capture its exact rationalization verbatim (RED), write the skill to counter that specific excuse (GREEN), then re-run under pressure and close any new loophole found (REFACTOR). systematic-debugging/CREATION-LOG.md documents this having actually been done for that skill (e.g. "Bulletproofing Elements... Language Choices... Structural Defenses," lines 33–47).

This is the most transferable idea in the set: it's a method for making instructive prose survive contact with a model that wants to shortcut it, independent of the specific domain (debugging, TDD, verification, or anything else).

Part 2 — How sage-mode compares, gap by gap

1. vs. gstack's gbrain (semantic memory / code intelligence)

Sage-mode has no equivalent. sage-recall is the plugin's only retrieval mechanism, and it is pure lexical BM25 — lib/recall/index.ts implements idf() (line 127) and bm25() (lines 132–148) directly, with no embedding call, vector store, or symbol/call-graph structure anywhere in lib/. find /root/fix/plugin/lib shows board, cli, consult, dag, evidence, lint, notebook, recall, review, setup, util — no code-intelligence module, no adapter contract, nothing that resolves "what calls this function" or "where is X conceptually implemented" beyond keyword match against docs/**/*.md and skills/**/SKILL.md (sage-recall/SKILL.md line 11).

sage-mode also has no analog to gbrain's cross-machine sync, per-repo trust triad, or the fail-closed egress-consent gate in contract.ts — but this is largely moot today because sage-mode has no feature that sends anything off-machine at all. If sage-mode ever adds gbrain-style memory sync, it currently has no security model to reuse; gstack's would need to be built from scratch.

Verdict: gstack is clearly ahead here, and it isn't close. BM25 keyword search over a project's own docs is a materially weaker retrieval mechanism than ranked semantic search plus call-graph navigation over the whole codebase.

2. vs. compound-engineering-plugin's verified cross-model review

Sage-mode gestures at cross-model review but has zero verification code for it — a materially different claim than it appears to make.

sage-mode's agent personas declare non-Claude models directly in frontmatter: agents/architect.md:4 (model: grok-4.6), agents/reviewer.md:4 and agents/red-team.md:4 (model: gemini-3.7-flash), and eight of the sixteen agents that declare a model use grok-4.5/grok-4.6 (confirmed via grep -n "^model:" agents/*.md). agents/red-team.md (lines 9–12) frames this as a second, genuinely independent reviewer: "Sequential second-wave reviewer... finds what they missed."

But nothing in lib/ verifies any of this actually happened. lib/consult/index.ts — the module backing sage's own "Lane B" second-opinion mechanism — only ever shells out to the claude CLI itself (spawnSync("claude", ...) at lines 47 and 106; a full-file grep for codex|gemini|openai|gpt|model.*provider|cross-model|receipt returns nothing). There is no extract_model_receipt-equivalent function anywhere in the plugin; lib/board/index.ts (lines 119, 132) merely displays whatever string is in a node's model field — it never checks it against anything the host actually reports. The entire mechanism depends on Cursor's agent runtime honoring the model: frontmatter field, which sage-mode's own research doc admits is unverified: docs/research/scorecard.md states plainly, "Cost control (10) assumes plugin-shipped subagents honor their model frontmatter — documented for .cursor/agents/, never stated for plugins... Both are an hour of testing" (§6). That hedge is real and honest — but it sits underneath a self-assigned score of 10/10 on Cost control, the single highest capability score anywhere in that document, for a mechanism with literally zero enforcing or verifying code in the repo I can point to.

Verdict: compound-engineering-plugin is decisively ahead. It ships a tested, receipt-verified cross-model pipeline that explicitly labels unverifiable routes as unverified. sage-mode ships a declared intention to use different models with no code that confirms, records, or falls back when that intention silently fails to hold — and its own scorecard both admits this and still scores it as if it were proven.

3. vs. superpowers' rationalization-resistant skill discipline

Sage-mode has genuinely and thoroughly adopted this pattern — but only at one of its two prompt layers, and without superpowers' pressure-testing practice.

Every one of sage-mode's 44 SKILL.md files (19 top-level in skills/*/SKILL.md, plus all 25 catalog skills in skills/catalog/*/SKILL.md) carries a "Common Rationalizations" table and a "Red Flags" section, confirmed by grep -rl "Common Rationalizations" skills/*/SKILL.md skills/catalog/*/SKILL.md returning all 44 files. The quality is comparable to superpowers' own, and in one respect arguably stricter: sage-retro/SKILL.md (lines 132–136, 153) requires that new rationalization-table entries be "read from its own transcript or blocker text, never invented for the occasion" — i.e., the same RED-phase discipline superpowers documents in writing-skills/testing-skills-with-subagents.md, but written as a standing procedural rule inside the product itself rather than a one-time authoring practice. sage-recall/SKILL.md (lines 20–25) and adr/SKILL.md (lines 20–28, in skills/catalog/adr/SKILL.md) show the same shape is followed consistently, not just in the flagship skills.

But this discipline stops at the skill layer. grep -rl "Common Rationalizations\|Rationalization" agents/*.md returns zero of the 19 files in agents/. agents/implementer-backend.md — the persona actually writing production code under time pressure — states the TDD rule as a single flat bullet with no surrounding defense: "Write a failing test first. Code written before its test exists is deleted, not adapted" (line 13), with no rationalization table, no red-flags list, nothing analogous to test-driven-development/SKILL.md's Iron Law framing or its "Thinking 'skip TDD just this once'? Stop. That's rationalization" (superpowers, line 29). The 19 agent briefs (architect.md, implementer-*.md, reviewer.md, red-team.md, etc.) are the layer doing hands-on, deadline-pressured work — precisely where superpowers' research says pressure-driven rationalization shows up — and it is the layer sage-mode left unhardened.

Separately, sage-mode has no equivalent of superpowers' TDD-of-skills practice. It has a real, partially-automated eval harness (test/evals.test.ts runs a tier-2 retrieval-accuracy check at lines 10–24, plus two mechanical fixture checks at lines 26–35), but the model-behavior scenarios that would actually test rationalization-resistance under pressure are only documented, not executed: evals/tier3/README.md lists eight scenarios ("Reviewer handed a diff with a planted auth bug," "Implementer asked to touch a file outside its lane," etc.) as things to "run... against a fixture repository," but only two of the eight (overlap dag is refused, planted finding survives the gate with evidence) actually appear in test/evals.test.ts. The top-level A/B gate is more blunt about it: evals/comparison.md opens with "Status: not yet run. No results recorded below or elsewhere in this repo... no prior run's numbers should be assumed to exist just because this file does" — sage-mode's own evidence-freshness discipline (see Part 3, item 6) applied to itself would call this exact claim STALE.

Verdict: mixed, and precisely bounded. At the skill layer sage-mode matches or slightly exceeds superpowers' rigor (44/44 files, plus a transcript-grounding requirement superpowers doesn't state as a standing rule). At the agent-persona layer it has none of it (0/19 files). And its process-effectiveness claims remain, by its own admission, unvalidated.

Part 3 — Gaps, prioritized

  1. sage-careful's MEDIUM tier has real, demonstrated bypasses that its gstack source did not have. hooks/sage-careful lines 174–178 match destructive commands with literal case substring patterns (*'rm -r'*, *'DROP TABLE'*, *'TRUNCATE'*) instead of the tokenized/regex checks gstack uses (careful/bin/check-careful.sh line 213: grep -qE 'rm\s+(-[a-zA-Z]*[rR]|--recursive)', catching any flag order). I ran both live: $ echo '{"tool_input":{"command":"rm -fr important-data/"}}' | sh sage-careful {} $ echo '{"tool_input":{"command":"rm --force --recursive important-data/"}}' | sh sage-careful {} $ echo '{"tool_input":{"command":"psql -c \"drop table users;\""}}' | sh sage-careful {} All three should ask for confirmation under sage-mode's own stated policy (skills/catalog has no entry for this, but the hook's own MEDIUM-tier comment at line 173 says "always ask") and all three return {} (silent allow). gstack's equivalent script explicitly lowercases before matching SQL keywords (check-careful.sh line 64, CMD_LOWER) specifically to avoid this. None of sage-mode's own test fixtures (hooks/tests/sage-careful/*.in.json — 16 named cases) cover rm -fr, --force --recursive, or lowercase SQL, so this regression ships un-caught by the plugin's own test suite. Severity: high — this is a security-relevant hook, this exact class of input is common (developers type -fr about as often as -rf), and the code comment at sage-careful lines 89–91 explicitly claims to mirror gstack's anchoring approach for the HIGH tier, which makes the MEDIUM-tier regression a same-file inconsistency, not an unrelated oversight.

  2. The cross-model "independent review" cost architecture has no verifying code, as detailed in Part 2 item 2 (lib/consult/index.ts lines 47, 106 only ever spawn claude; agents/architect.md:4, agents/reviewer.md:4, agents/red-team.md:4 declare grok-4.6/gemini-3.7-flash with nothing checking it happened). Severity: high — this underpins sage-mode's headline differentiator per its own docs (docs/research/scorecard.md §5: "Cost architecture (10, and the next best is 8)... Nobody else routes work across an included lane, a flat-rate subscription lane, and a metered lane").

  3. No semantic or call-graph code search; retrieval is BM25-over-docs only (lib/recall/index.ts lines 127–148; see Part 2 item 1). Severity: medium-high — this limits how well any sage-mode skill can navigate a codebase it hasn't been told exactly where to look in, and it's the single most load-bearing capability gstack has that sage-mode entirely lacks.

  4. The anti-rationalization pattern is applied inconsistently — 44/44 in skills/, 0/19 in agents/ (Part 2 item 3, confirmed by direct grep of both directories). Severity: medium — the un-hardened layer is exactly the one under the most execution pressure.

  5. Sage-mode's own effectiveness claims are unvalidated by its own admission. evals/comparison.md (full file, 20 lines) states the sage-vs-plain-agent A/B has never been run. evals/tier3/README.md's eight process-adherence scenarios are 75% (6/8) not wired into any automated test (test/evals.test.ts covers only 2 of them). Severity: medium — process-heavy tooling that adds real overhead (eight commands, four hooks, a notebook renderer, an evidence ledger — sage-mode's own docs/research/scorecard.md §6 lists this) needs to demonstrate the overhead pays for itself, and by its own documentation it currently hasn't tried to measure that.

  6. Learning capture is single-pass with no external grounding or automated claim validation, unlike compound-engineering-plugin's ce-compound, which dispatches six specialist research subagents (skills/ce-compound/references/agents/*.md: best-practices-researcher, framework-docs-researcher, pattern-recognition-specialist, security-sentinel, performance-oracle, data-integrity-guardian) and runs scripts/validate-doc-claims.py / validate-frontmatter.py before writing. sage-retro/SKILL.md step 3 (lines 33–61) drafts a learning directly from what the orchestrator itself observed this sprint, with no independent research pass and no automated claim-checking script anywhere in lib/ or skills/sage-retro/. Severity: medium — sage-retro's dedup/staleness-sampling discipline (Part 4) is genuinely strong, but the learnings it captures are less independently grounded than compound-engineering-plugin's.

  7. Sage-mode is Cursor-only; the other three ship real multi-host portability. compound-engineering-plugin and superpowers both maintain live conversion targets for a dozen-plus hosts (compound-engineering-plugin/.codex-plugin, .cline, .devin-plugin, .grok-plugin, .kimi-plugin, .omp-plugin, .opencode, .pi; superpowers/.codex-plugin, .devin-plugin, .hermes-plugin, .kimi-plugin, .opencode, .pi), and gstack defines an explicit host abstraction (hosts/define-host.ts, hosts/claude.ts, hosts/codex.ts, hosts/cursor.ts, hosts/kiro.ts, hosts/opencode.ts, etc.). sage-mode ships a single .cursor-plugin/plugin.json and nothing else. Severity: medium — this is an adoption/reach gap more than a quality gap, but it's a real one.

  8. No secrets-redaction or tamper-evident egress ledger. gstack's lib/redact-engine.ts (540 lines), lib/redact-patterns.ts (775 lines), and lib/egress-receipt.ts (392 lines) form a real, fail-closed system that blocks secret-shaped content from leaving the machine and records a receipt before any sync. sage-mode has no file addressing this anywhere in lib/. Severity: low today (sage-mode doesn't sync anything off-machine yet), but a real design debt if cross-session/cross-machine memory (gap #3) is ever added — there is currently nothing to reuse.

Part 4 — Overall verdict

Against gstack specifically: gstack wins decisively on two fronts sage-mode has no real answer to — semantic/graph code intelligence (gap #3) and a security-hardened memory-sync path (gap #8) — both backed by a mature, running system rather than a design intent. On the one area where the two systems overlap most directly, destructive-command guardrails, sage-mode's own hook is a close structural port of gstack's (the HIGH tier's tokenized-flag-cluster matching is faithfully reproduced, down to a code comment citing gstack's approach at sage-careful lines 89–91) but the port introduced a concrete regression in the MEDIUM tier (gap #1) that the original does not have. Sage-mode did successfully port and generalize gstack's more sophisticated idea — content-addressed, tree-hash-based evidence freshness (lib/evidence/index.ts's wtree(), lines 33–68, plus a deliberately conservative mtime fingerprint at lines 78–100 to catch mutate-then-revert races) — into a mechanically enforced Stop-hook (hooks/sage-proof) that re-prompts up to three times before giving up with a written warning, rather than gstack's model, where the equivalent check lives in the careful/freeze skill layer. That is a genuine, code-verified strength. Net: gstack is currently the more capable and more trustworthy system; sage-mode has correctly identified and re-implemented gstack's best idea (evidence freshness) but is behind on gstack's other headline capability (memory/code-intelligence) and has a same-family regression in the capability it copied most literally (careful).

Against compound-engineering-plugin specifically: compound-engineering-plugin's verified cross-model receipt mechanism (Part 1) is real, tested, and does something sage-mode's cost/independence architecture only claims to do without any enforcing code (gap #2) — this is the sharpest finding in this review, because it's precisely the mechanism sage-mode's own scorecard names as its single best-differentiated capability. compound-engineering-plugin's learning-capture pipeline is also more rigorously grounded (gap #6), though sage-mode's retro discipline around deduplication and bounded staleness-resampling (sage-retro/SKILL.md steps 3–4) is comparably careful about not letting the corpus rot, which is a real strength on its own axis. compound-engineering-plugin also ships genuine multi-host portability (gap #7) that sage-mode doesn't attempt. Net: compound-engineering-plugin is ahead on the exact axis sage-mode claims as a differentiator, and ahead on portability; sage-mode is arguably ahead on retro-cycle discipline (dedup + bounded staleness sweep) but that's a narrower claim than "verified independent review."

Against superpowers specifically: this is sage-mode's closest and most favorable comparison. Sage-mode has adopted superpowers' signature rationalization-resistant prose pattern at real scale (44/44 skill files) and, in the retro skill, added a discipline superpowers doesn't formalize (rationalization-table entries must trace to an actual transcript, not be invented). Sage-mode also has a mechanically stronger multi-agent coordination primitive than superpowers offers: hooks/sage-lane is a fail-closed preToolUse hook (hooks/hooks.json, failClosed: true) that denies an out-of-lane Write/Delete at the tool-call level with symlink-safe path resolution and dual Python/Node implementations, whereas superpowers' dispatching-parallel-agents/SKILL.md handles the same "don't let agents step on each other" concern entirely through advisory prose ("Check for conflicts," lines 165) with no enforcement layer at all. Where sage-mode falls short of superpowers is exactly gap #4 (the discipline doesn't reach the agent-persona layer) and the absence of superpowers' documented pressure-testing methodology for validating that its own prose actually holds under pressure (gap #5) — superpowers at least has a named practice and a creation log showing it was followed once (systematic-debugging/CREATION-LOG.md); sage-mode's comparable claims remain, by its own file's own words, unrun. Net: sage-mode is close to competitive with superpowers on skill-prose discipline and ahead of it on mechanical multi-agent enforcement, but behind it on validating that any of this actually works, and behind it on maturity/reach (superpowers ships to twice as many hosts and, per its own marketplace metadata, is at major version 6.3.0 with an established user base — a claim I could not independently verify beyond the repo's own version string, but which is at minimum consistent with a shipped, versioned product rather than a repo whose own comparison eval has never been run).

Against the best-of-all-three bar: sage-mode does not currently clear it on any single axis examined here. Its strongest, most independently verifiable wins are (a) the evidence-freshness Stop-hook, which is a real improvement in mechanical enforcement over how gstack expresses the same idea, and (b) the fail-closed lane-ownership hook, which is stricter than superpowers' equivalent advisory pattern. Against that: it has no code-level analog to gstack's semantic memory, no code-level analog to compound-engineering-plugin's verified cross-model review (its own most-claimed differentiator), a documented rationalization-resistance pattern applied to only half its prompt surface, and a concrete, live regression in the one hook it ported most literally from gstack.

On sage-mode's documentation overstating what the code does — the specific defect this review was asked to flag: docs/research/scorecard.md scores sage-mode's "Cost control" at 10/10 — the single highest score in its entire 12-dimension table, ahead of every real, shipped competitor — for a mechanism (multi-model agent dispatch) that has zero verifying code anywhere in lib/ and that the same document, one section later, admits is an unverified assumption about host behavior ("Cost control (10) assumes plugin-shipped subagents honor their model frontmatter... never stated for plugins"). A design that is honestly labeled as unverified in prose but still carries the maximum possible score in the same document's own scoring table is not a hedge — it's a live inconsistency, and it's the report's own words that expose it, not an external critique. Separately, that same document's "Memory / compounding" score of 9/10 for sage-mode (ahead of gstack's 7 and compound-engineering-plugin's 8, the only two systems in the comparison with any real memory implementation) rests entirely on BM25 keyword search over the project's own docs (lib/recall/index.ts), with no semantic search, no external grounding, and no automated claim validation — capabilities both of the systems it's scored above actually have in code. Both figures should be read as design aspiration presented with the confidence of a measured result.
