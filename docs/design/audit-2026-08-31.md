## 2. What is genuinely good

### 2.1 The evidence ledger is faithful to gstack and hardened past it

`lib/evidence/index.ts` implements gstack's content-addressed working-tree fingerprint correctly — temp-index copy to preserve the stat cache, `git add -A` against the copy, `write-tree`, TOCTOU double-snapshot, `sha256(command)` binding, allow-paths. Verified live in a scratch repo: a run recorded FRESH, an appended byte to an unrelated file flipped it to `STALE tree changed: app.js`.

The original contribution beyond gstack is `checkSageIgnored()`. sage's own writes (`evidence.jsonl`, run logs, worktree checkouts) land between the pre- and post-run snapshots; if `.sage/` and `.worktrees/` are not gitignored the TOCTOU guard correctly refuses to record a fingerprint and every subsequent check grades STALE forever, with a reason string an operator cannot act on. The code detects that condition via `git check-ignore` and fails loud with the fix. That is a real bug class, correctly reasoned about, that gstack does not appear to guard.

### 2.2 The enforcement layer is tested harder than any of the three references test theirs

277 unit tests pass. The hook golden-payload suite runs every hook against both `bash` and `dash` in both Cursor and Claude Code payload shapes — which is the right paranoia, since `/bin/sh` is `dash` on ubuntu-latest and the CI comment records that this exact issue shipped once already. `sage-careful` handles BOM-prefixed stdin, `${IFS}` word-splitting, base64-piped-to-shell, flag-order and case variants, compound-command fallthrough. `sage-lane` denies on a missing path rather than allowing. Deny-tier hooks carry `failClosed: true`. CI runs tests, build, lint, and hook goldens.

### 2.3 Context economy is the decisive structural win over gstack

Measured on the local checkouts:

| | core SKILL.md lines | skills |
|---|---|---|
| gstack | 62,244 | 61 |
| sage-mode | 3,465 (+996 catalog) | 13 (+25 catalog) |
| compound-engineering | 2,859 | 34 |
| superpowers | 3,377 | 14 |

v3 proposed replacing gstack's 862-line duplicated preamble with a 425-line always-apply rule. What shipped is 161 lines, and it is denser and better than the 425 would have been — decision brief, evidence rule, anti-sycophancy, scope valve, non-interactive semantics, plan mode, context health, completion status, repo ownership. Losing 264 planned lines here is an improvement, not a shortfall.

### 2.4 The cost architecture's premises check out against reality

Verified against Cursor's live docs today: `grok-4.6`, `grok-4.5`, `composer-2.5` are the included pool; `gemini-3.7-flash` and the `gpt-5.6-*` family are metered third-party. Every model ID in every role card is a real, currently-available model in the right pool. No other plugin in the reference set pins a model per role at all — gstack's subagents pin nothing. `extractModelReceipt()` reads the `modelUsage` field back off `claude -p --output-format json` and refuses to mark a call verified when the field is absent, which is the correct posture.

### 2.5 The review pipeline works end to end

Verified live: `review scope` computed scope booleans and diff size from the union of committed + working-tree + untracked changes; `review select` returned a roster from those booleans; `review gate` rejected a row missing `category` with a reason and a non-zero exit; a CRITICAL/confidence-9 finding with empty evidence was capped to 5 and had its fingerprint computed. `dag validate` refused a cycle (`D1: cycle: n1 -> n3 -> n1`) and an `owns` intersection (`D2: n1 and n2 intersect`), both with exit 1.

### 2.6 The catalog is real content

The prior adversarial review found the 25 catalog skills were one template with names swapped. That is fixed. Sampled `incident-triage` and `perf-profile`: both carry specific, opinionated procedure (CPU vs. wall-clock profiling and why a CPU sampler is blind to blocked time; mitigate-before-root-cause with the reasoning), rationalization tables, and observable done-conditions. This is now better lifecycle coverage than superpowers has, and comparable to agent-skills.

## 3. Where it falls short

### 3.1 The two load-bearing spikes have still never been run — and the plugin's own IRON LAW forbids this

`SPIKE-01` (does `preToolUse`'s `tool_input` carry a file path for Write?) and `SPIKE-02` (do plugin-shipped subagents honor `model:` frontmatter?) are both `status: not-run`. I independently re-read Cursor's hook documentation: `preToolUse`'s `tool_input` is documented only for Shell (`command`, `working_directory`). The payload shape for Write/Edit is genuinely unspecified. `afterFileEdit` *is* documented to carry `file_path` — which is why the `sage-lane-after` detect-and-revert fallback exists, unregistered.

Consequences if they fail: SPIKE-01 FAIL demotes lane enforcement from preventive to probabilistic-then-corrected, and phase 5 (parallel worktrees) needs re-estimating. SPIKE-02 FAIL means Lane A/B/C — the single most differentiated idea in the design — is not wired at all, and every implementer, reviewer and red-team run silently costs whatever the session model costs.

The repo is built around `NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE` and it shipped v1.0.0 with its two most consequential claims carrying no evidence. That is the finding, not the spikes themselves.

Partial mitigation already exists and is undocumented: `sage setup` writes 19 role cards into `<project>/.cursor/agents/`, which *is* the SPIKE-02 fallback path. SPIKE-02.md still says "nothing in this repo currently installs a project-local copy under `<project>/.cursor/agents/`." That sentence is false as of the current code.

### 3.2 The eval harness reports a false FAIL, and nothing runs it

`node evals/tier3/run.js` → **6 passed, 1 failed, 1 skipped.** The failure is `Reviewer handed a diff with a planted auth bug — expected exactly 1 finding to survive gate, got undefined`.

The gate is correct. The runner is wrong. `scenario2()` does `JSON.parse(out.stdout) as Finding[]`, but `review gate --json` emits `{ "findings": [...], "rejected": [] }`. `findings.length` is `undefined`. Confirmed by running the command directly: the CRITICAL finding survives with its `x-api-key` evidence intact. One-line fix.

The real problem is that `grep -rn "tier3\|evals"` across `.github/workflows/ci.yml` and `package.json` returns nothing. The tier-3 suite is wired nowhere. A red signal has been sitting in the repo, invisible, behind a green CI badge — which is the precise failure mode §8.7's "absence of proof is never proof of absence" exists to prevent, occurring inside the tool that preaches it.

### 3.3 There is no evidence the process is worth its overhead

`evals/comparison.md` states it plainly: *"Status: not yet run."* And its own stakes sentence is the right one — *"If sage-mode is not better on defects-escaped, the process is ceremony."*

The reference plugins all have something here. superpowers ships a documented PR-rejection rate and runs evals against its own skill text. gstack has telemetry from daily use. compound-engineering's dogfooding is visible in 73 test files and a changelog of real fixes. sage-mode has 28 commits, ~5,800 lines of runtime TypeScript, 10,571 lines of documentation, and **zero sprints run through it.** Not one roadmap, not one spec, not one dag, not one build, not one ship.

### 3.4 The surface is sprint-shaped only — this is the biggest usability gap

The stated goal is a tool for daily engineering work that scales speed. The minimum unit of value in sage-mode is a whole sprint behind four approval gates. `/sage-plan` step 1 explicitly refuses when no approved roadmap exists. `/sage-shape` is a long one-question-at-a-time interrogation on the rate-limited Lane B.

There is no skill for: debugging a failure, fixing one bug, reviewing an arbitrary PR, doing a quick refactor behind a test, spinning a worktree for a parallel experiment. `grep -rln "debug\|bug fix\|hotfix\|one-off\|small change"` across `skills/*/SKILL.md` matches exactly one file, and it is `design-build`.

Compare what the references actually get used for. superpowers' most-reached-for skills are `systematic-debugging`, `test-driven-development`, `using-git-worktrees`, `verification-before-completion` — all standalone, all usable in any session, zero ceremony. compound-engineering has `/ce-work` for a single unit of work. Those are the Tuesday-afternoon skills. sage-mode has none of them.

The scorecard already predicted this — *"If sage-mode is not usable at the end of phase 1, the design is wrong"* — and then phase 1 shipped as the two slowest, most gated commands in the system. A tool that only pays out on week-shaped work will get reached for a few times a quarter, and a tool reached for a few times a quarter compounds nothing.

### 3.5 Memory is project-local, so nothing compounds across projects

`sage recall` indexes `docs/**/*.md` in the current project plus the shipped catalog. Learnings, decisions and reviews live under `<project>/docs/` and `<project>/.sage/`. A learning earned in project A is unreachable from project B.

For a personal tool used across several repos, this fragments the compounding n ways — and compounding is the entire reason the notebook exists. compound-engineering's thesis is precisely that last month makes this month cheaper; its learnings folder is at least a single place. The `learning-format.md` design (`applies_when` as the retrieval key, `last_confirmed`, `status: superseded`) is genuinely the best learning-record schema in the reference set, and it is currently pointed at a silo.

### 3.6 The docs have drifted from the code, in a repo whose thesis is evidence-bound accuracy

- `scorecard.md` §6: *"Maturity: 1. Zero lines of code."* There are now ~5,800 lines of runtime TypeScript and 277 passing tests.
- `SPIKE-02.md`: *"nothing in this repo currently installs a project-local copy under `<project>/.cursor/agents/`."* `sage setup` writes 19 of them; I watched it.
- `architecture-v3` §7: `sage-shape/SKILL.md` at *"~830 lines of substance."* Actual: 427 lines + ~225 in references. The content survived; the number did not.

Individually minor. Collectively: the documentation is the least evidence-bound artifact in a repo built on evidence-binding, and it is 10,571 lines — more than the runtime it describes.

### 3.7 Claude Code support is a half-port with a hole its own manifest documents

`plugin/.claude-plugin/plugin.json` carries a `_comment_no_rules` field admitting that `rules/sage-conduct.mdc` has no delivery mechanism on Claude Code and that its content *"still needs to reach Claude Code sessions somehow… but that redelivery is NOT solved by this manifest."*

On Claude Code, then, the decision-brief format, the evidence rule, anti-sycophancy, the scope valve, non-interactive semantics, plan-mode discipline, context health and completion-status protocol all silently fail to load. That is the entire behavioral spine of the system.

The reference set shows what real multi-host costs: compound-engineering ships nine host converters backed by ~73 test files; superpowers ships eight-plus hosts with per-host test directories. Multi-host is a program, not a manifest. Either fold the conduct content into an always-loaded skill for that host and test it, or declare Cursor-only and delete the second manifest.

### 3.8 Minor

- **Review scope does not exclude sage's own installed files.** `.sage/` and `.worktrees/` are excluded; the 19 role cards `sage setup` writes into `.cursor/agents/` are not. In the smoke repo this produced 878 diff lines of sage's own agent cards and lit up `SCOPE_AI`, which on Lane C is money spent reviewing sage-mode's own prose.
- **`sage recall` prints escaping relative paths** for catalog hits (`../mnt/.../skills/catalog/doc-release/SKILL.md`). Cosmetic, but a path that walks out of the project reads as a bug.
- **`TODO(cli)` in `lib/evidence/index.ts:177`** — `lib/cli.ts` does not thread an explicit sprint through `evidencePath()`.

## 6. The uncomfortable read

The build quality here is high and the reasoning in the code comments is better than most production codebases carry. That is not in question.

What is in question is the ratio. Twenty-eight commits, ~5,800 lines of runtime, 10,571 lines of docs about the runtime, 277 tests, five design revisions, three prior self-reviews — and the tool has not yet been used to build anything, once. The eval that would tell you whether any of it pays for itself was written and never run. This is a well-engineered answer to a question that has not been asked yet.

The correct next action is not another feature and not another review. It is a sprint.
